### Client-Side Stack

| Component | Technology | Rationale & Tradeoffs |
| :--- | :--- | :--- |
| **UI Framework** | **Svelte** | **Why Svelte?** Svelte is a compiler, not a framework. It shifts the bulk of the work to build time, resulting in highly optimized, vanilla-like JavaScript with minimal runtime overhead. This leads to faster load times, a smaller memory footprint, and better performance on constrained devices. Its component-based architecture is modern and developer-friendly.<br><br>**Alternative (Vanilla JS):** While the absolute lightest option, it can become complex to manage state and UI updates as the application grows. Svelte provides structure without a significant performance penalty.<br><br>**Why not React/Vue?** They use a Virtual DOM, which adds a layer of abstraction and increases the library size and memory usage, making them less ideal for low-end hardware. |
| **Local Database**| **Dexie.js + PouchDB** | **Why Dexie.js?** Dexie provides a clean, modern, and powerful wrapper around IndexedDB, making it much easier to work with. It supports complex queries, indexing, and is highly performant.<br><br>**Why PouchDB?** PouchDB is the key to our seamless sync. It's a JavaScript implementation of the CouchDB protocol. By using PouchDB on the client, we can leverage its built-in replication capabilities to sync with a CouchDB or PouchDB-Server backend with minimal custom code.<br><br>**Combined:** Dexie will be used for all application-level data access (reading/writing products, sales), while PouchDB will work under the hood, managed by the Service Worker, to handle the synchronization with the server. |
| **QR/Barcode Scanning** | **BarcodeDetector API** | **Why BarcodeDetector?** It's a native browser API, which means it will be the most performant and energy-efficient option. It's supported in Chrome/Edge on Android.<br><br>**Fallback (jsQR):** For browsers that don't support the BarcodeDetector API (like Firefox or Safari on iOS), jsQR is a lightweight and reliable pure-JavaScript library that can be used as a fallback. |
| **Service Worker** | **Custom + Workbox**| **Why Custom?** We'll need a custom service worker to handle the background sync logic with PouchDB. This gives us fine-grained control over the synchronization process.<br><br>**Why Workbox?** For caching static assets, Workbox (a library from Google) simplifies the process and reduces boilerplate code. We'll use it to implement a "stale-while-revalidate" strategy for our assets, ensuring the app loads quickly while also staying up-to-date. |

### Server-Side Stack

| Component | Technology | Rationale & Tradeoffs |
| :--- | :--- | :--- |
| **Backend API** | **Go (Gorilla Mux)** | **Why Go?** Go is compiled to a single, small binary with no external dependencies, making deployment incredibly simple. It has excellent performance, a low memory footprint, and its concurrency model is well-suited for handling I/O-bound tasks like API requests. This makes it a perfect choice for resource-constrained devices like a Raspberry Pi.<br><br>**Alternative (Node.js - Fastify):** Node.js is also a strong contender. It's single-threaded and event-driven, which is great for I/O. However, for a CPU-bound task or in a memory-constrained environment, Go's performance and efficiency can be superior. Deployment is also slightly more complex with Node.js (requires `node` runtime, `npm/yarn`, `node_modules`). |
| **Database** | **CouchDB** | **Why CouchDB?** CouchDB is the ideal database for this project. Its master-master replication is the killer feature, designed for distributed systems and occasionally-connected clients. It's schema-less (flexible), and its use of HTTP as its API makes it easy to interact with. Its "eventual consistency" model is a good fit for this application.<br><br>**Alternative (PouchDB-Server):** A lightweight, Node.js-based implementation of the CouchDB API that uses a local file-based storage system. It's a great option for an even more minimal setup, especially if you're already using Node.js for the backend. It's not as battle-tested or feature-rich as CouchDB but is sufficient for this project's needs.<br><br>**Why not a traditional RDBMS (Postgres/MySQL)?** They require a more structured schema, and implementing a robust, conflict-free synchronization mechanism would be a significant undertaking. |
| **Authentication**| **JWT** | **Why JWT?** JSON Web Tokens are stateless. The server creates a token, signs it, and sends it to the client. The client then includes this token in the header of subsequent requests. The server can verify the token without needing to store any session information, which is ideal for a lightweight, scalable, and distributed system. |
