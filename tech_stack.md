### Client-Side Stack

| Component | Technology | Rationale & Tradeoffs |
| :--- | :--- | :--- |
| **UI Framework** | **Vue.js** | **Why Vue.js?** Vue.js offers a great balance between performance, features, and ease of use. It has a smaller runtime footprint than React and provides excellent documentation and a strong ecosystem. Its component-based architecture is intuitive, and its reactivity system is highly optimized. For a mobile-first PWA, Vue's performance is more than adequate, and its developer experience is top-notch.<br><br>**Why not Svelte/VanillaJS?** While Svelte is lighter, Vue.js has a more mature ecosystem and a larger community, which can be beneficial for long-term maintenance. The performance difference on modern low-end devices is often negligible for this type of application. |
| **Local Database**| **Dexie.js + PouchDB** | **Why Dexie.js?** Dexie provides a clean, modern, and powerful wrapper around IndexedDB, making it much easier to work with. It supports complex queries, indexing, and is highly performant.<br><br>**Why PouchDB?** PouchDB is the key to our seamless sync. It's a JavaScript implementation of the CouchDB protocol. By using PouchDB on the client, we can leverage its built-in replication capabilities to sync with a CouchDB or PouchDB-Server backend with minimal custom code.<br><br>**Combined:** Dexie will be used for all application-level data access (reading/writing products, sales), while PouchDB will work under the hood, managed by the Service Worker, to handle the synchronization with the server. |
| **QR/Barcode Scanning** | **BarcodeDetector API** | **Why BarcodeDetector?** It's a native browser API, which means it will be the most performant and energy-efficient option. It's supported in Chrome/Edge on Android.<br><br>**Fallback (jsQR):** For browsers that don't support the BarcodeDetector API (like Firefox or Safari on iOS), jsQR is a lightweight and reliable pure-JavaScript library that can be used as a fallback. |
| **Service Worker** | **Custom + Workbox**| **Why Custom?** We'll need a custom service worker to handle the background sync logic with PouchDB. This gives us fine-grained control over the synchronization process.<br><br>**Why Workbox?** For caching static assets, Workbox (a library from Google) simplifies the process and reduces boilerplate code. We'll use it to implement a "stale-while-revalidate" strategy for our assets, ensuring the app loads quickly while also staying up-to-date. The Vue CLI has excellent integration with Workbox. |

### Server-Side Stack

| Component | Technology | Rationale & Tradeoffs |
| :--- | :--- | :--- |
| **Backend API** | **Python (FastAPI)** | **Why FastAPI?** FastAPI is a modern, high-performance Python web framework. It's built on Starlette and Pydantic, which gives it incredible speed (on par with Node.js and Go) and automatic data validation and API documentation (Swagger UI/ReDoc). Its asynchronous nature is perfect for I/O-bound operations, and its dependency injection system makes it easy to write clean, testable code. It's an excellent choice for a lightweight, maintainable, and performant API.<br><br>**Alternative (Flask):** Flask is a classic Python micro-framework. It's very flexible but requires more boilerplate for features like data validation and async operations. FastAPI provides these out of the box, making it a more productive choice for this project. |
| **Database** | **CouchDB** | **Why CouchDB?** CouchDB is the ideal database for this project. Its master-master replication is the killer feature, designed for distributed systems and occasionally-connected clients. It's schema-less (flexible), and its use of HTTP as its API makes it easy to interact with. Its "eventual consistency" model is a good fit for this application.<br><br>**Alternative (PouchDB-Server):** A lightweight, Node.js-based implementation of the CouchDB API that uses a local file-based storage system. While we are using Python for the backend, `pouchdb-server` could still be run as a separate, minimal process if an extremely lightweight setup is desired. |
| **Authentication**| **JWT** | **Why JWT?** JSON Web Tokens are stateless. The server creates a token, signs it, and sends it to the client. The client then includes this token in the header of subsequent requests. The server can verify the token without needing to store any session information, which is ideal for a lightweight, scalable, and distributed system. |
